# ShortX — URL Shortener

ShortX is a URL shortener built with Node.js, Express, and PostgreSQL. It converts long URLs into compact, shareable short codes and redirects users to their original destinations.

The project focuses on backend fundamentals, REST API design, database constraints, input validation, and reliable URL redirection.

## Features

- Generate 8-character Base62 short codes.
- Store URL mappings in PostgreSQL.
- Redirect short URLs to their original destinations.
- Validate URLs and allow only HTTP and HTTPS protocols.
- Use parameterized SQL queries to prevent SQL injection.
- Handle duplicate short-code collisions with bounded retries.
- Return appropriate HTTP status codes for invalid requests and missing URLs.
- Run PostgreSQL locally using Docker Compose.

## Getting Started

### 1. Clone the repository

```bash
git clone <YOUR_GITHUB_REPOSITORY_URL>
cd ShortX
```

Replace the placeholder with your actual repository URL.

### 2. Install dependencies

```bash
npm install
```

Run this from the repository root if the root package uses npm workspaces. Otherwise, install dependencies in the API package directory.

### 3. Configure environment variables

Create the appropriate environment file for the API, using the existing project configuration as the source of truth.

Example:

```env
PORT=3000
DATABASE_URL=postgresql://shortx_user:shortx_password@localhost:5432/shortx
```

- `PORT`: Port on which the API server listens.
- `DATABASE_URL`: PostgreSQL connection string.

The values above are local-development examples. Make sure they match the database credentials and port configured in `docker-compose.yml`.

Never commit real credentials, production secrets, or environment files containing secrets. Add them to `.gitignore` where appropriate.

### 4. Start PostgreSQL

From the repository root, start the PostgreSQL service defined in Docker Compose:

```bash
docker compose up -d postgres
```

If the Compose service has a different name, replace `postgres` with the actual service name.

Verify the container status:

```bash
docker compose ps
```

### 5. Apply the database schema

Run the SQL migration or schema initialization command already configured by the project.

Ensure the `urls` table contains the columns required by the API:

- `id`
- `original_url`
- `short_code`
- `created_at`

The `short_code` column must have a unique constraint so that duplicate codes cannot be stored.

### 6. Start the API

Use the development script configured in the API package's `package.json`. For example, if the script is named `dev`:

```bash
npm run dev
```

Run the command from the directory containing that script, or use the corresponding npm workspace command from the repository root.

The API should be available at:

```text
http://localhost:3000
```

## API Documentation

The examples below assume the API uses the `/api/urls` route prefix and returns JSON for creation and error responses.

### 1. Create a short URL

**Endpoint:** `POST /api/urls`

**Content-Type:** `application/json`

Request:

```json
{
  "original_url": "https://example.com/articles/backend"
}
```

Example successful response (assuming the API returns `201 Created`):

```json
{
  "id": 1,
  "original_url": "https://example.com/articles/backend",
  "short_code": "aB3xY7kP",
  "created_at": "2026-10-18T10:30:00.000Z"
}
```

The returned values are illustrative; the actual ID, short code, and timestamp are generated by the application and database.

### 2. Redirect to the original URL

**Endpoint:** `GET /api/urls/:shortcode`

Example:

```http
GET http://localhost:3000/api/urls/aB3xY7kP
```

Expected behavior:

- Look up the short code in PostgreSQL.
- If the code exists, redirect to the original URL using an HTTP redirect status, typically `302 Found`.
- If the code does not exist, return `404 Not Found` with a JSON error response.

Example not-found response:

```json
{
  "error": "Short URL not found"
}
```

## Validation and Error Handling

The URL creation endpoint should handle invalid requests consistently.

| Scenario | Expected status |
|---|---:|
| Missing `original_url` | 400 Bad Request |
| Malformed URL | 400 Bad Request |
| Unsupported protocol | 400 Bad Request |
| Nonexistent short code | 404 Not Found |
| Successful URL creation | 201 Created, if used by the controller |
| Unexpected server or database error | Appropriate 5xx status |

Only `http:` and `https:` protocols are accepted.

Example invalid request:

```json
{
  "original_url": "ftp://example.com"
}
```

Example validation response:

```json
{
  "error": "Only HTTP and HTTPS URLs are allowed"
}
```

The exact error messages and success status codes should match the implementation in the API controllers and middleware.

## Collision Handling

ShortX generates short codes using Base62 characters. Because generated codes can theoretically collide, PostgreSQL enforces uniqueness on `short_code`.

When an insertion fails with PostgreSQL error code `23505` for the short-code unique constraint, the service generates a new code and retries a limited number of times. Other database errors are propagated rather than treated as collisions.

## Testing

Use Postman to test the API.

Recommended test cases:

1. Create a short URL with a valid HTTPS address.
2. Create a short URL with a valid HTTP address.
3. Submit a request without `original_url`.
4. Submit a malformed URL.
5. Submit a URL with an unsupported protocol.
6. Request a nonexistent short code.
7. Simulate a duplicate short-code collision and verify retry behavior.

Confirm the HTTP status, JSON response, and database state for each case.
